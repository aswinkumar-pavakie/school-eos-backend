GLOBAL RULES THAT APPLY TO EVERY LOGIN BELOW
--------------------------------------------------------------------------------
- Every screen after login sends `Authorization: Bearer <access-token>`
  (device logins — 9 and 10 — use a device credential instead).
- Every list screen supports pagination; never fetch "all" in one call.
- A 404 means "not found or not yours" — show a generic not-found state,
  never reveal whether the record exists for someone else.
- A 409 means a conflict (duplicate, state, concurrency) — show the
  specific conflict, never a generic "error occurred."
- A 422 means a business rule was broken — show the rule, not a stack trace.
- Any screen that creates or changes money, a boarding record, a card
  tap, or a wallet balance MUST send an `Idempotency-Key` header,
  generated once per user action and reused only on retry of that
  exact action.
- Web screens are desk-based: real tables, server-side pagination,
  bulk actions. Mobile screens are stand-up, one-hand, offline-tolerant
  where the workflow says so.

################################################################################
LOGIN 1 — ADMIN                                                          [WEB]
The heaviest login in the product. Now also owns Transport and Hostel setup.
################################################################################

--------------------------------------------------------------------------------
W1.1 LOGIN & DASHBOARD
--------------------------------------------------------------------------------
1. Standard login -> POST /api/v1/auth/login
2. GET /api/v1/me -> confirm Admin role and permissions.
3. Dashboard on load, fetch in parallel (not sequentially):
   - Enrolment count, staff count, today's attendance %
   - Fee collection this month vs target
   - Open complaints / incidents count
   - Pending approvals awaiting Admin
   - Hostel occupancy summary
   - Transport fleet status summary
   - Any expiring vehicle/driver documents (surfaced proactively, not
     buried — this is the kind of thing that gets missed until it's a
     compliance problem)

--------------------------------------------------------------------------------
W1.2 STUDENT RECORDS
--------------------------------------------------------------------------------
CREATE / EDIT:
1. GET /api/v1/students (paginated, filterable by section/status/medium)
2. Create: POST /api/v1/students -> then link guardian(s):
   POST /api/v1/students/{id}/guardians
3. Bulk import: use the Bulk Operations feature.
   POST /api/v1/bulk-jobs (type=student-import) -> upload file -> poll
   GET /api/v1/bulk-jobs/{id} until complete -> show per-row errors from
   GET /api/v1/bulk-jobs/{id}/errors, never a single pass/fail summary.
4. Section/medium transfer, sibling linking, document upload (birth
   certificate, TC, community certificate) — standard CRUD screens against
   the Students & Guardians endpoint group.
5. Exit / TC issuance: mark status, generate certificate.
   POST /api/v1/students/{id}/exit (or equivalent transition)
   POST /api/v1/certificates/transfer-certificates

--------------------------------------------------------------------------------
W1.3 STAFF RECORDS & ROLE ASSIGNMENT
--------------------------------------------------------------------------------
1. GET /api/v1/staff -> list, filter by department/teaching status.
2. Create staff -> POST /api/v1/staff
3. Assign a role or a Faculty assignment (Class Advisor, Academic
   Coordinator, Health In-Charge, stage In-Charge, Community In-Charge,
   Sports Faculty):
   POST /api/v1/staff/{id}/role-assignments
   Scope picker matters here — assigning Class Advisor must ask WHICH
   section; assigning Academic Coordinator must ask school-wide or which
   stage; assigning Sports Faculty must ask WHICH sport(s)/team(s) (see
   W1.5a). Do not let this be a free-text field. None of these
   assignments — Sports Faculty and Academic Coordinator included —
   grant any web access; Faculty is mobile-only regardless of
   assignment.

--------------------------------------------------------------------------------
W1.3a STAFF BIOMETRIC ATTENDANCE — SETUP, OVERSIGHT & MANUAL FALLBACK
--------------------------------------------------------------------------------
SETUP (once, at installation):
1. Register the biometric terminal the same way any other device is
   registered — this is not a special case.
   POST /api/v1/devices  { deviceType: "BIOMETRIC_TERMINAL", location: "Main Gate" }
2. Configure the returned device credential into the physical terminal
   (or the development simulator, before real hardware arrives).
3. Enroll each staff member's face/fingerprint on the device itself
   (this happens on the vendor's device/SDK, not through your API — the
   device only ever sends you the RESULT of a match, never the biometric
   data).

DAILY OVERSIGHT:
1. GET /api/v1/staff/attendance?dateFrom=X&dateTo=Y
   -> a real data table: staff name, event type, method (biometric vs
   manual), state (confirmed/pending/rejected), timestamp.
2. Filter by method=MANUAL to see every fallback entry at a glance —
   this is the screen that tells Admin whether the terminal has been
   unreliable this week, which is worth knowing on its own.

MANUAL FALLBACK — TWO DIFFERENT PATHS, BUILD BOTH:
1. ADMIN DIRECT ENTRY (Admin/Principal physically present, device down):
   POST /api/v1/staff/attendance/manual
   { staffId, eventType, occurredAt, reason: "Terminal offline" }
   -> written CONFIRMED immediately. No approval step — Admin's own
   entry is the authority here.
2. APPROVING A FACULTY SELF-REPORT (device was down, Admin wasn't at the
   gate to see it):
   GET /api/v1/approvals?requestType=STAFF_ATTENDANCE_MANUAL_ENTRY&status=pending
   -> review the reason the Faculty member gave.
   POST /api/v1/approvals/{id}/approve  or  /reject
   -> this is the SAME generic approvals screen used for every other
   approval type in the product (concessions, refunds, outings). Do not
   build a separate "attendance approvals" screen — one inbox, filtered
   by request type, same as everywhere else.

WHY THIS IS TWO PATHS AND NOT ONE: a Faculty member reporting their own
attendance can never be self-confirming — that defeats the entire
purpose of a fallback check. Admin/Principal recording it directly is
fine, because they're an independent party vouching for it, not the
person whose attendance is in question.

--------------------------------------------------------------------------------
W1.4 ADMISSIONS
--------------------------------------------------------------------------------
1. Enquiry pipeline: GET /api/v1/admissions/enquiries
2. Application review: GET /api/v1/admissions/applications/{id}
3. Seat allotment, admission fee collection, then convert to a full student
   record — this should be one guided flow, not four disconnected screens.
   POST /api/v1/admissions/applications/{id}/convert

--------------------------------------------------------------------------------
W1.5 TRANSPORT SETUP (moved here from the former Transport Manager role)
--------------------------------------------------------------------------------
VEHICLES:
1. GET /api/v1/transport/vehicles
2. POST /api/v1/transport/vehicles -> registration, capacity, ownership.
3. Document tracking (insurance, fitness, permit, PUC) with expiry —
   surface expiring documents on the dashboard (W1.1), don't make Admin
   go looking for this.
4. Activate/deactivate: POST .../activate, POST .../deactivate

ROUTES & STOPS:
1. GET /api/v1/transport/routes
2. Create route -> add stops in sequence with geofence radius:
   POST /api/v1/transport/routes/{id}/stops
3. Map view for stop placement is strongly preferred over lat/long text
   entry — this is where operator error creates real problems later
   (wrong geofence radius, stops out of sequence).

DEVICES (GPS trackers, terminals):
1. GET /api/v1/devices -> register a new GPS tracker or NFC terminal.
   POST /api/v1/devices
2. Assign a device to a vehicle or a counter:
   POST /api/v1/devices/{id}/assignments

STUDENT ALLOCATION:
1. Assign a student to a route + stop:
   POST /api/v1/transport/student-assignments
2. Capacity is checked server-side against the vehicle seat count — the
   UI should show remaining capacity per stop/route before Admin submits,
   not just fail after the fact.

DRIVERS / ATTENDANTS:
1. Standard CRUD with licence + police verification expiry tracking,
   same document-expiry pattern as vehicles.

INCIDENTS:
1. GET /api/v1/transport/incidents -> review, close.
   PATCH /api/v1/transport/incidents/{id}
   POST /api/v1/transport/incidents/{id}/close

LIVE FLEET VIEW:
1. Map showing all active trips.
   GET /api/v1/transport/trips?status=active
2. Per-trip detail including the boarding board:
   GET /api/v1/transport/trips/{id}/student-status
3. This is a genuinely useful oversight screen for Admin even though the
   Bus Attendant app (Part 2) is where boarding actually happens — Admin
   should be able to see, in real time, which trips have unresolved
   NOT_BOARDED exceptions right now.

--------------------------------------------------------------------------------
W1.5a SPORTS STRUCTURE & EQUIPMENT (moved here from the former Sports Manager role)
--------------------------------------------------------------------------------
Rarely-touched setup work, same rhythm as Transport and Hostel setup
above: Admin owns the structure and assets, Sports Faculty (Part 2,
Faculty login, section 1.14) runs the day-to-day team operations
against what Admin sets up here.

SPORTS, CATEGORIES, FACILITIES, EQUIPMENT:
1. Define sports and age/gender categories:
   POST /api/v1/sports
   POST /api/v1/sport-categories
2. Facility master records (courts, grounds, pools):
   POST /api/v1/sports/facilities
3. Equipment master inventory — this is the "important sports
   management" that stays with Admin even though issue/return is a
   daily Sports Faculty task:
   POST /api/v1/sports/equipment
   GET /api/v1/sports/equipment-issues (oversight view — who currently
   has what, across every team, without needing to ask each Sports
   Faculty member individually)

COACH ASSIGNMENT:
1. Coach records — internal (a staff member already holding the Sports
   Faculty assignment) or external (with police verification expiry
   tracked the same way as a transport driver's documents).
2. Assign a coach to a team:
   POST /api/v1/sports/teams/{id}/coaches
3. A coach with expired verification cannot be assigned — enforced
   server-side; surface the expiry clearly before Admin attempts the
   assignment, not just fail after.

MARKING A FACULTY ACCOUNT AS SPORTS FACULTY:
1. This is not a separate screen — it is the exact same Faculty
   assignment flow used for Class Advisor, Academic Coordinator,
   Health In-Charge, and Community In-Charge (see W1.3 above), usable
   at staff creation/admission time or at any later point in that
   staff member's record:
   POST /api/v1/staff/{id}/role-assignments
   { assignmentType: "SPORTS_FACULTY", scope: { sportIds / teamIds } }
2. Scope picker matters here exactly as it does for Class Advisor's
   section picker — ask WHICH sport(s)/team(s) this assignment covers,
   never leave it as an unscoped grant. This is what keeps a Sports
   Faculty member's app limited to their own teams and not the whole
   school's sports program.

--------------------------------------------------------------------------------
W1.6 HOSTEL SETUP (structure and allocation — Warden has NO access to this)
--------------------------------------------------------------------------------
STRUCTURE:
1. Create the hostel hierarchy once: hostel -> blocks -> floors -> rooms
   -> beds.
   POST /api/v1/hostels
   POST /api/v1/hostels/{id}/blocks
   POST /api/v1/hostel-blocks/{id}/rooms
   POST /api/v1/hostel-rooms/{id}/beds
2. This is rarely-touched setup work, mainly at the start of a year or
   when physical capacity changes. Build it as a tree/hierarchy editor,
   not a flat list — the room count per school makes a flat list unusable
   past a small hostel.

ALLOCATION:
1. Assign a student to a specific bed:
   POST /api/v1/hostel/allocations (or the specific allocation endpoint —
   confirm exact path in your build against the Hostel feature group)
2. Occupancy view: which beds are filled, which are vacant, by block/floor.
   GET /api/v1/hostels/{id}/blocks (drill down through the hierarchy)
3. This is the ONLY place a student-to-bed assignment can be created or
   changed. The Warden app can only READ this allocation to build its
   roll-call roster — enforce this server-side via the access rules
   already defined in the API document, not just by hiding the UI here.

--------------------------------------------------------------------------------
W1.7 CERTIFICATES
--------------------------------------------------------------------------------
1. Template-driven generation: TC, bonafide, conduct, study certificate.
   POST /api/v1/certificates/{type}
2. Serial-numbered register, reprint tracking — GET the issue history
   before allowing a reprint, and log every reprint as its own event, not
   a silent overwrite.

--------------------------------------------------------------------------------
W1.8 ID CARDS
--------------------------------------------------------------------------------
1. Issue batch: select students/staff, generate card records, export a
   print file for the card vendor.
   POST /api/v1/nfc/cards (bulk creation)
2. Block a lost/damaged card:
   POST /api/v1/nfc/cards/{id}/suspend (or equivalent)
3. Approve and issue a replacement (charged through the fee ledger, not
   the wallet):
   POST /api/v1/finance/... (replacement fee) then re-provision the card.
4. Card provisioning itself is a DEVICE-authenticated flow at the
   personalisation station — Admin's role here is authorising the token,
   not performing the cryptographic write:
   POST /api/v1/nfc/cards/{id}/provisioning-token

--------------------------------------------------------------------------------
W1.9 COMMUNITIES, COMPLAINTS, OPERATIONS
--------------------------------------------------------------------------------
1. Create communities, assign a Faculty Community In-Charge:
   POST /api/v1/communities
2. Publish school-wide notices:
   POST /api/v1/announcements
3. Administrative complaint queue (non-restricted categories only —
   bullying/harassment/staff-conduct route to a restricted committee
   queue, not here):
   GET /api/v1/complaints?category=administrative
4. Inventory, purchase requests, vendor records — standard CRUD screens.

--------------------------------------------------------------------------------
W1.10 CAMPS SETUP
--------------------------------------------------------------------------------
1. Create camp, register partner agency, define sessions and services.
   POST /api/v1/camps
   POST /api/v1/camp-partners
   POST /api/v1/camps/{id}/services
2. Announce to the target audience:
   POST /api/v1/camps/{id}/announce
3. Participant-level work (attendance, checkup findings) happens on the
   Faculty and Health In-Charge mobile apps (Part 2) — Admin's job here
   ends at setup and announcement.

--------------------------------------------------------------------------------
W1.11 REPORTS & BULK EXPORTS
--------------------------------------------------------------------------------
1. Standard reports: attendance trends, fee collection, enrolment by
   category/medium, dropout/long-absence, syllabus coverage.
   GET /api/v1/reports/{report-type}
2. Large reports run async — POST to trigger, poll or get notified when
   the download is ready, never block the browser tab.
3. State education portal export (manual upload elsewhere, not a live
   integration) — generate the file in the required format from here.

--------------------------------------------------------------------------------
PRINCIPAL — MOBILE HALF (the web half lives in the ADMIN-adjacent section
above under "PRINCIPAL"; this covers decisions made away from the desk)
--------------------------------------------------------------------------------
This was previously only referenced, never written out. Written here in full.

DASHBOARD (lighter than the web version — summary tiles, not full tables):
1. GET /api/v1/reports/leadership-dashboard?view=summary
2. Tiles: attendance % today, fee collection this month, open complaints,
   pending approvals awaiting Principal, any open SOS incidents.
3. Tapping any tile opens a simple read-only detail list — NOT the full
   drill-down tables that exist on the web dashboard. If a Principal
   needs to export or print something, the app should say so and point
   them to the web app rather than trying to replicate a data table on
   a phone screen.

APPROVALS INBOX:
1. GET /api/v1/approvals?assignedRole=principal&status=pending
2. One list, every request type mixed together (fee concessions, hostel
   outings, mark corrections, staff attendance manual entries) — sorted
   by how close each is to its SLA deadline, oldest/most urgent first.
3. Tap an item -> see the request detail and the reason given ->
   Approve or Reject with an optional comment.
   POST /api/v1/approvals/{id}/approve
   POST /api/v1/approvals/{id}/reject
4. This is the SAME approvals engine as everywhere else in the product —
   there is no "mobile-only" approval type. If it can be approved on
   web, it can be approved here, and vice versa.

ANNOUNCEMENTS:
1. Compose -> audience picker (whole school / class / medium / group /
   single person) -> publish.
   POST /api/v1/announcements
2. This is the one place a non-emergency announcement is sent from
   mobile just as easily as from web — no reason to force a Principal
   back to a desk for a routine notice.

EMERGENCY / SOS — the single most safety-critical screen in this login:
1. Always reachable, one tap away from anywhere in the app, not buried
   in a menu.
2. Requires re-authentication (PIN or biometric unlock) before it fires
   — this is deliberate friction to prevent an accidental trigger, not
   an obstacle to a genuine emergency.
   POST /api/v1/incidents/sos
3. On confirm, this triggers the tiered escalation server-side — the
   app does not need to know or manage the escalation tiers, it only
   needs to fire the request and show "Help alerted" clearly.
4. If the SOS relates to a live transport incident, show the affected
   vehicle's frozen last-known position directly on this confirmation
   screen, not as a separate step to go find it.

LIVE BUS MAP:
1. GET /api/v1/transport/trips?status=active
2. Map showing every active trip's current position, refreshed every
   15 seconds while this screen is open.
3. This is oversight, not operations — tapping a vehicle shows its
   route and current student boarding status
   (GET /transport/trips/{id}/student-status) but this screen has no
   edit actions. Route changes, driver reassignment, all of that stays
   on the web Admin screens.

LOOKUP:
1. A single search bar -> search any student, staff member, or class by
   name.
2. Results show a read-only summary card — attendance, recent marks,
   fee status for a student; role and assignments for a staff member.
3. This exists so a Principal standing in a hallway, talking to a
   parent or a teacher, can pull up relevant information in seconds
   without needing to be at a desk. Keep it fast and keep it read-only.

################################################################################
LOGIN 5 — FACULTY                                                        [APP]
Class Advisor, Academic Coordinator, Health In-Charge, stage In-Charge,
Community In-Charge, and Sports Faculty are ASSIGNMENTS on this same
login, not separate apps. NONE of them — Academic Coordinator included —
unlock a web app anymore. Faculty is mobile-only, always. (There is no
Sports Manager login; its former end-to-end sports operations move into
this login's Sports Faculty assignment, section 1.14 below. Sports
structure/equipment stays with Admin, W1.5a.)
################################################################################

--------------------------------------------------------------------------------
1.1 LOGIN & SESSION
--------------------------------------------------------------------------------
1. Faculty opens the app -> Login screen (email/mobile + password).
2. Submit -> POST /api/v1/auth/login
3. On success -> store access token + refresh token securely (Keychain /
   Keystore, never plain storage).
4. Call GET /api/v1/me -> returns identity, roles, and effective permissions.
   Use this response to decide which extra menu items to show (Class
   Advisor, Academic Coordinator, Health In-Charge, Community In-Charge —
   whichever assignments this faculty member actually holds).
5. If token expires mid-session -> silently call POST /api/v1/auth/refresh
   before retrying the failed request. Only force re-login if refresh fails.
6. Logout -> POST /api/v1/auth/logout -> clear local tokens -> back to
   Login screen.

--------------------------------------------------------------------------------
1.2 HOME / TODAY SCREEN
--------------------------------------------------------------------------------
1. On load -> fetch today's timetable for this faculty member.
   GET /api/v1/timetable/slots?facultyId=me&date=today
2. Show current period highlighted, rest of the day below.
3. Fetch substitution duties assigned to them for today.
   GET /api/v1/timetable/substitutions?facultyId=me&date=today
4. Fetch pending tasks badge count (ungraded homework, pending marks entry

   POST /api/v1/transport/taps/sync (or the boarding-specific sync
   endpoint if separate in your build — confirm with backend).
4. A student tapping who is NOT allocated to this route -> full-screen
   WRONG BUS warning, does not silently succeed.
5. Manual override for a student whose card fails to read:
   Same boardings endpoint, source=ATTENDANT_MANUAL, no tapEventId.
6. On DROP trips, same flow with direction=ALIGHT. An ALIGHT with no
   prior BOARD for that student on this trip will be rejected — if this
   happens, it usually means the wrong trip is selected; surface that
   possibility in the error message, don't just show a raw 422.

--------------------------------------------------------------------------------
4.4 CLOSE BOARDING
--------------------------------------------------------------------------------
1. Before the vehicle leaves the last stop, or at trip end -> "Close
   Boarding" button.
2. POST /api/v1/transport/trips/{id}/boarding/close
3. This is what turns every still-EXPECTED student into NOT_BOARDED and
   fires the parent alert server-side. Show a brief summary before
   confirming ("3 students still not boarded — closing will alert their
   parents") so the attendant has one last chance to fix a missed
   manual entry first.

--------------------------------------------------------------------------------
4.5 SOS
--------------------------------------------------------------------------------
1. Always visible, always reachable, requires a confirm-tap.
2. POST /api/v1/incidents/sos (transport context)
3. Also usable to report a breakdown or delay without a full SOS — a
   separate, less alarming "Report Issue" button for non-emergencies.

--------------------------------------------------------------------------------
4.6 WHAT THIS LOGIN MUST NEVER SHOW
--------------------------------------------------------------------------------
Marks, fees, addresses, phone numbers, or any guardian detail. This
login's API responses are already scoped server-side to name + photo +
stop only — do not add client-side code that fetches or caches anything
beyond that, even for convenience.

################################################################################
LOGIN 9 — CANTEEN VENDOR                                                 [APP]
Device-scoped. The sale screen is the highest-stakes screen in the product.
################################################################################

--------------------------------------------------------------------------------
5.1 LOGIN & SHIFT
--------------------------------------------------------------------------------
1. Operator login (may be device-bound per terminal, confirm with backend).
2. Open shift: enter opening float amount.
   POST /api/v1/canteen/shifts (or equivalent — confirm exact endpoint
   name with backend if not explicitly listed)
3. Idle screen after shift opens: "Tap card" — this is the default resting
   state the app returns to after every transaction.

--------------------------------------------------------------------------------
5.2 SALE — THE CORE FLOW
--------------------------------------------------------------------------------
1. Idle screen shows "Tap card."
2. On tap -> resolve credential -> fetch student + wallet snapshot.
   (This should be a single fast call; if your build separates these,
   fire them together, not sequentially.)
3. Screen fills with STUDENT PHOTO (large), NAME, CLASS, BALANCE.
   THIS IS THE SECURITY CONTROL — do not make the photo small or
   secondary to anything else on screen.
4. Cashier visually confirms the child matches, then either:
   a) enters an amount (amount-only mode), or
   b) selects items from the menu (item-level mode)
   GET /api/v1/canteen/menu-items (loaded once at shift start, cached
   locally, not re-fetched per sale)
5. Confirm -> server checks in order: card not blocked, wallet active,
   within per-transaction cap, within daily cap, no item block, balance
   sufficient (or within grace allowance). Each of these has ITS OWN
   distinct rejection screen — never collapse them into one generic
   "Payment failed."
   POST /api/v1/canteen/transactions (with deviceIdempotencyKey)
6. On success -> brief on-screen receipt, then auto-return to idle after
   a few seconds. Do not require a manual "Done" tap for the common case
   — that adds friction to every single sale during a lunch rush.
7. Parent is notified server-side automatically. No client action needed.

--------------------------------------------------------------------------------
5.3 REJECTION SCREENS (each must be visually distinct, not a shared modal)
--------------------------------------------------------------------------------
- Card blocked
- Wallet frozen
- Over daily limit
- Item blocked by parent (name the specific item)
- Insufficient balance (show the shortfall amount)

A generic failure screen encourages the cashier to just re-tap, and
re-tapping is exactly how double charges happen if idempotency isn't
respected client-side too (always reuse the same deviceIdempotencyKey
on a retry of the same attempted sale, never generate a new one).

--------------------------------------------------------------------------------
5.4 PRE-ORDER COLLECTION
--------------------------------------------------------------------------------
1. Separate mode/tab from a fresh sale.
2. GET /api/v1/canteen/pre-orders?forDate=today&status=paid
3. On tap -> match against a pre-order for that student -> confirm
   collection. NO photo-confirmation gate needed here (already paid and
   authorised at order time) — this should be visibly FASTER than a
   fresh sale.
   POST /api/v1/canteen/pre-orders/{id}/collect

--------------------------------------------------------------------------------
5.5 OFFLINE SALES  [OFFLINE]
--------------------------------------------------------------------------------
1. If connectivity drops mid-shift, do not stop the counter.
2. Cache at shift start: roster, photos, balances, limits, item blocks,
   card blocklist (with its version number).
3. Allow sales up to the configured offline floor per student per day.
   Queue locally with deviceIdempotencyKey.
4. If the blocklist is older than the configured max age -> REFUSE
   payment taps entirely, show "Offline too long — payment unavailable,"
   do not silently allow a possibly-blocked card through.
5. On reconnect -> auto-sync:
   POST /api/v1/canteen/transactions/sync
   Handle ACCEPTED / DUPLICATE / REJECTED per item exactly as in 1.3.

--------------------------------------------------------------------------------
5.6 SHIFT CLOSE
--------------------------------------------------------------------------------
1. End of day -> enter declared cash total (if any cash side-sales exist
   outside the wallet system).
2. System shows its own recorded total; variance is calculated, not
   hidden, even if it doesn't reconcile to zero.
   POST /api/v1/canteen/shifts/{id}/close
3. Settlement view (read-only for the vendor, Finance manages the actual
   settlement approval):
   GET /api/v1/canteen/settlements?vendorId=me

================================================================================
CROSS-REFERENCE — FORMER "SPORTS MANAGER" TASKS
================================================================================
There is no Sports Manager role. That login's end-to-end sports
operations split the same way Transport Manager's tasks did:
- Structure and assets — defining sports/categories, facility master
  records, equipment master inventory, and coach assignment — now live
  under Login 1 — Admin, section W1.5a.
- Day-to-day operations — teams, rosters, student sport profiles and
  participations, trials, training sessions, tournaments, fixtures,
  results, rankings, achievements, certificates, facility bookings, and
  equipment issue/return — move to Login 5 — Faculty, as a new
  permission assignment called Sports Faculty, section 1.14. Admin
  grants this assignment (and can grant it at admission time, the same
  moment a student — or in this case a staff record — is first set up,
  or at any later point) the same way it grants Class Advisor or
  Academic Coordinator: W1.3, `POST /api/v1/staff/{id}/role-assignments`.
There is no "Coach" login either — an internal coach is simply a
Faculty member holding the Sports Faculty assignment for that team; an
external coach is a records-only entry Admin manages alongside the
assignment, with the same police-verification-expiry tracking a
transport driver's documents get.
